# 작업 C-1 — 첫 리모델링 구현 규칙

작성일: 2026-09-20. 기준 커밋: `41bc092` (B-3 완료).

기존 `01 GDD v1.0` / `02 Economy v0.1` / `03 Progression v0.1` / `05 채택기록 v1`과
실제 엔진(`src/engine`)을 대조해 정리했다. **이 문서는 구현 전 규칙 정리이며
리모델링 코드를 포함하지 않는다.**

목표: 1단계 매장에서 조건을 충족해 기존 테이블·직원을 보존한 채 2단계로 확장하고,
7번째 테이블을 구매해 운영할 수 있게 한다.

범위 밖: 화면·애니메이션, 오프라인 환산, 중규모 대회. 기존 밸런스 상수는 바꾸지 않는다.

---

## A. 확정 기준

### A-1. 시작 조건 (Progression §5, GDD §8)

| # | 조건 | 엔진 판정 |
|---|---|---|
| 1 | 1단계 매장에 테이블 **6개 설치** | `venue.stage === 1 && installedTableCount(state) >= 6`. 미운영 테이블도 센다 |
| 2 | 인지도 **50 이상** | `venue.awarenessMilli >= milli(50)` |
| 3 | 소규모 대회 **정상 완료 2회 이상** | `records.completedTournaments.filter(c => c.scale === 'small').length >= 2` |
| 4 | 예약·정리·진행 상태의 **대회 없음** | `state.tournament === null` |
| 5 | 필요 현금 확보 | A-2 |

**딜러 6명은 조건이 아니다** (GDD §8 명시, Progression P07).
근무 딜러가 3명이어도 다른 조건이 맞으면 리모델링할 수 있어야 한다.

**긴급 운영 중에는 시작할 수 없다.** 이미 `commands.ts`의 `EMERGENCY_ACTIVE` 관문이
모든 명령을 막으므로 새 코드 없이 성립한다 (05 §7-4).

### A-2. 비용과 운영 예비금 (Progression §5)

```text
T        = 현재 일반 세션이 모두 끝날 때까지의 최대 잔여 게임시간
C_before = 정리 동안 발생할 시간당 비용의 보수적인 상한
C_after  = 기존 배치를 새 매장에 유지했을 때의 시간당 운영비
필요 현금 = 15000 + T x C_before + 4 x C_after
```

- 기존 `minuteCosts()`에서 파생한다. **새 비용 계산 엔진을 만들지 않는다.**
- 정리 중 배치가 변하지 않으므로 `C_before = C_after = minuteCosts(state).total x 60`이
  보수적 상한이자 정확값이다.
- `T = ceil((max(session.endsAtMinute) - 현재 분) / 60)`. 세션이 없으면 0.
- **정리 기간에 발생할 매출을 조건 충족 자금으로 미리 계산하지 않는다.**

문서 예시와 일치해야 한다: 일반 딜러 6명 + 서비스 직원 1명이면
`C_after = 760G/게임시간`, 전환 후 예비금 `3,040G`, `T = 2시간`이면 필요 현금 최대 `19,560G`.

### A-3. 상태 전환 (Progression §6)

```text
일반 영업 -> REMODEL_PREPARING -> (단일 전환 작업) -> 2단계 영업
```

**요청과 준비**

- 요청 시 조건을 다시 검사하고 고유 작업 ID를 만든다.
- 15,000G를 `lock()`으로 잠근다. `cash`는 줄지 않고 `availableCash`만 줄어든다 (05 §3).
- 신규 방문 생성을 멈춘다. 기존 대기 손님은 안내 후 해산시킨다.
- **해산은 서비스 불만으로 계산하지 않는다** — 이탈 집계에 넣지 않는다 (B-2 참조).
- 착석 중인 손님은 정상 세션을 끝내고 정해진 매출을 발생시킨다.
- 정리 중 급여·시설비·매장 운영비는 **계속 낸다.**
- 만족도는 준비 기간 **고정**한다 (`stepSatisfaction` 건너뜀).
  일반 세션 완료에 따른 인지도와 매출은 정상 반영한다.
- 진입 시 충족한 인지도·실적 조건을 준비 중 **재평가해 취소하지 않는다.**
- 새 테이블 구매, 직원 배치 변경, 추가 지출, 대회 예약을 잠근다.
- 준비 상태에서도 저장·복원이 가능해야 한다.

**자산 전환** (모든 일반 세션 완료 시, 하나의 원자적 작업)

- 테이블·직원·시설의 **기존 ID와 레벨·보유 상태를 보존**한다.
- 보존 대상: 현금, 인지도, 만족도, 직원 보상 수령 기록
  (`skilledDealerAwarded` / `tournamentSpecialistAwarded`),
  대회 실적(`tournamentsDone`, `completedTournaments`),
  개최권 사용 기록(`usedTournamentDays`), 홍보 대기 시간(`promoReadyMinute`), 게임 시각.
- `venue.stage = 2`. 현재 테마는 유지하고 두 번째 테마를 선택 가능 상태로 해금한다.
- 기존 6개 테이블을 1층 대응 설치 지점으로 배치한다 (`floor: 1`, `spotIndex` 유지).
  가능한 기존 직원 배치를 유지하고 대기 직원은 대기로 유지한다.
- 2층 지점 7~18을 구매 가능 상태로 연다. **테이블을 무료로 추가하지 않는다.**
- `settleLocked(15,000G)`로 잠금 해제와 지출 확정을 **각각 한 번씩** 처리한다.
- 완료 ID를 저장해 같은 ID 재처리로 비용·해금이 중복되지 않게 한다.

**재개**

전환 완료 **다음 경제 분부터** 2단계 수요와 기존 배치로 영업한다.
별도의 현실 시간 공사 대기를 추가하지 않는다. 연출 콜백으로 자산을 지급하지 않는다.

### A-4. tick 처리 순서 통합

현재 9단계는 `processUnlocks -> processStaffRewards -> (긴급 축소 | 배치 전환)`이다.
여기에 리모델링을 더한다.

```text
9) processUnlocks -> processStaffRewards -> processRemodel
   -> (emergency ? processEmergency : applyPendingDealerChanges)
```

세션 정산은 4단계이므로 **마지막 세션이 분 M에 정산되면 전환은 같은 분의 9단계**에서
일어난다. (대회 준비 완료가 3단계라 M+1인 것과 다르다 — 9단계는 4단계보다 뒤다.)

2단계 수요는 5단계에서 계산되므로 전환 다음 분부터 자연히 적용된다.
Progression §6의 "전환 완료 다음 경제 분부터"와 일치한다.

### A-5. 기존 엔진이 자동으로 따라오는 부분

`venue.stage`만 바꾸면 아래가 전부 따라온다. **밸런스 상수를 손댈 필요가 없다.**

| 항목 | 근거 |
|---|---|
| 테이블 상한 6 -> 18 | `derive.ts` `canInstallMoreTables`가 `capByStage[stage]` 참조 |
| 7번째 테이블이 2층 | `commands.ts` `buyTable`의 `floor = index >= 7 ? 2 : 1` |
| 2단계 기본 수요 3.5 -> 6 | `demand.ts` / `derive.ts`가 `baseByStageMilli[stage]` 참조 |
| 대기 정원 8 -> 16 | `seating.ts`가 `capacityByStage[stage]` 참조 |
| 7번째 구매 시 대기 일반 딜러 자동 배치 | `buyTable`의 기존 동작 (Progression §7) |

### A-6. 저장과 버전

- 새 상태: `GameState.remodel` 타입 확대(현재 `null` 전용), 완료 기록/시퀀스 카운터.
- `saveVersion` 4 -> 5. `rulesVersion`도 올린다 (9단계에 처리가 추가되므로).
- v4 -> v5 마이그레이션: **`remodel`은 작업 A(v1)부터 필수 필드였으므로 초기화하지 않고
  `null` 값만 확인한다.** 새 `records` 카운터만 0/1로 초기화한다 (05 §7의 필수 필드 규칙).
- `assertSupported`의 `REMODEL_NOT_IMPLEMENTED`를 준비·전환 단계 허용으로 교체한다.
- 준비 중·전환 직후 각 시점에서 직렬화 왕복이 동일해야 한다.

### A-7. 투자 예상치 연결

리모델링은 준비비 잠금 + 지연 정산 구조가 대회와 같다.
따라서 **일반 `forecast()`는 리모델링 상태·명령을 계속 명시적 미지원으로 돌려보낸다.**
전용 진입점(`forecastRemodel`)은 C-2 이후로 미룬다. B-2C에서 확립한 경계를 그대로 따른다.

## B. 확정된 결정 (사용자 지정, 2026-09-20)

B-1~B-5는 검토 시점에 미정이었다. 아래가 **확정값**이며 구현은 이 절을 기준으로 한다.
표의 "검토 시 추천"은 그때의 제안이고, 결정이 다르면 결정이 우선한다.

### B-1. 준비 중 긴급 운영 — **① 리모델링 우선** (검토 시 추천 ①)

긴급 운영 진입과 **부족액 지원금 지급은 B-3대로 정상 처리**하되,
**테이블·딜러 축소만 리모델링 완료까지 유예**한다.

지켜야 할 불변식 (전부 인수 테스트로 고정한다):

| # | 불변식 |
|---|---|
| 1 | 잠긴 15,000G를 일반 운영비로 쓰지 않는다 |
| 2 | 지원금이 리모델링 비용 자체를 대신 내지 않는다 |
| 3 | 진행 중인 일반 세션을 중단하거나 미정산 상태로 삭제하지 않는다 |
| 4 | 공사 중 기존 테이블·딜러 배치를 유지한다 |
| 5 | 완료 시 테이블·직원 ID와 자산을 보존한다 |
| 6 | 리모델링 완료가 긴급 운영을 임의로 종료시키지 않는다 |
| 7 | 완료 후에도 긴급 상태가 유지되면 **다음 정상 B-3 처리 시점**에 유예된 축소를 적용한다 |
| 8 | 공사 중에 정상 지원 종료 조건을 충족했다면 이후 불필요한 축소를 실행하지 않는다 |
| 9 | 지원금 지급과 리모델링 비용 정산은 각각 정확히 1회 처리한다 |

**구현 결과 — 검토 시 예상한 "한 줄 추가"로는 부족했다.**

불변식 7과 8은 서로 반대 방향이라 "축소를 건너뛴다" 한 줄만으로는 둘 다 만족하지 못한다.
공사 중 종료 판정이 없으면 8이 깨지고(완료 다음 분에 B-3가 매장을 1테이블로 줄였다가
같은 틱에서 곧바로 종료한다), 무조건 종료시키면 6이 깨진다.
그래서 `processEmergency` 앞에 **유예 분기와 전용 종료 판정**을 함께 넣었다.

- `processEmergency`는 `state.remodel !== null`이면 자원을 건드리기 전에 분기한다.
  종료 조건을 충족하면 축소 없이 긴급 운영을 끝내고, 아니면
  `emergencyDownsizeDeferred` 이벤트만 남기고 돌아간다.
- 유예 중 종료 기준액은 **B-3와 같은 잣대**를 쓴다. B-3의 자금 조건은
  "**축소 완료 상태의** 분당 반복 비용 x 240"이므로, 유예 중에도
  *축소했다면 남았을 배치*(유지 테이블 1개 + 담당 딜러 1명 + 매장 기본비)로 기준액을 만든다.
  현재(축소 전) 배치 비용으로 재면 기준액이 실제 B-3보다 커져 불변식 8이 깨진다.
  새 상수는 만들지 않고 기존 급여·시설비·매장비 설정값과 `perMinuteUnits`만 쓴다.
- 잠긴 리모델링 비용은 `availableCash`에서 이미 빠져 있으므로 지원액 계산과
  종료 판정 어느 쪽에도 섞이지 않는다 (불변식 1, 2).
- `processRemodel`은 tick 9단계의 **마지막**에 둔다. 그래야 완료된 분에는 긴급 상태가
  그대로 남고, 유예된 축소는 다음 분의 `processEmergency`가 정상 경로로 처리한다 (불변식 7).

### B-2. 대기 해산과 이탈률 윈도우 — **통계에 허위 기록을 넣지 않는다** (검토 시 추천 ①)

공사로 인한 대기 손님 해산은 **일반적인 이탈로 계산하지 않는다.**
`arrivals`에도 `abandons`에도 넣지 않는다.

- 해산은 `remodelQueueDissolved` 이벤트로만 남기고 `recordWindow`를 호출하지 않는다.
- 공사 중에도 `recordWindow(state, 0, 0)`은 매 분 호출한다. 윈도우를 멈추는 것이 아니라
  **실제로 방문이 0, 이탈이 0이었다는 사실을 그대로 기록**하는 것이다.
- 공사 중에는 만족도 갱신을 고정하므로 `L = 0`이 그 기간의 만족도를 끌어올리지 않는다.

### B-3. 2단계 수요 — **기존 설정값 유지, 완료 다음 게임 분부터 적용** (검토 시 추천 ①)

2단계 수요 설정값은 그대로 둔다. 밸런스 상수를 이번 작업에서 바꾸지 않는다.
적용 시점은 **리모델링 완료 다음 게임 분부터**다.
완료된 분 자체는 5단계 수요 계산이 이미 지나간 뒤 9단계에서 단계가 바뀌므로,
`stage = 2` 수요는 그다음 분의 5단계에서 처음 반영된다.

전환 직후 이탈률이 높게 유지되는 현상은 **버그가 아니라 현재 밸런스의 결과**다.
회귀 감지용으로 인수 테스트에 수치를 고정한다 (05 §6의 미해결 과제로 계속 남긴다).

### B-4. 7번째 테이블 — **무료 지급 없음, 16,000G 유지** (검토 시 추천 ①)

7번째 테이블은 공짜로 주지 않는다. 가격 16,000G를 유지하고,
**정상 영업 매출로 실제로 구매·배치·운영**되어야 한다.

> 특정 테스트 상태의 리모델링 직후 잔액을 모든 플레이의 고정 잔액으로 가정하지 않는다.

따라서 인수 테스트 R16은 자금을 주입하지 않는다. 대신
**리모델링 직후 잔액이 테이블 값에 못 미치는 상태**에서 출발해 그 사실을 먼저 단언하고,
모자란 금액을 영업으로 모으는 구간까지 실제로 돌린다.
6명이 모두 근무 중이므로 7번 테이블 담당 딜러도 별도로 고용한다.
늘어난 일회성 지출이 테이블 값 + 고용비와 정확히 일치하는지,
긴급 지원금이 섞이지 않았는지까지 확인한다.

### B-5. 준비 중 명령 차단 사유 — **`REMODEL_ACTIVE` 신설** (검토 시 추천대로)

새 사유 `REMODEL_ACTIVE`를 도입하고 기존 `REMODEL_IN_PROGRESS`는 그대로 둔다.
둘은 의미가 다르며 서로를 대체하지 않는다.

| 사유 | 의미 | 발생 지점 | 도입 |
|---|---|---|---|
| `REMODEL_ACTIVE` | **지금 이 명령을 실행할 수 없다** — 공사 중에는 일반 명령 전반을 막는다 | `commands.ts`의 공통 관문. `EMERGENCY_ACTIVE` 검사 바로 다음 | C-1 |
| `REMODEL_IN_PROGRESS` | **대회를 열 수 없다** — 대회 자격 판정 자체의 결론 | `tournament.ts`의 `planSmallTournament` | B-1 |

두 사유는 동시에 성립할 수 있다. 공사 중 `reserveSmallTournament`를 넣으면
`validateCommand`는 앞선 공통 관문에서 `REMODEL_ACTIVE`를 돌려주지만,
`planSmallTournament`를 직접 호출하면 `REMODEL_IN_PROGRESS`가 그대로 나온다.
**공통 관문이 생겼다고 해서 대회 자격 판정의 사유를 지우지 않는다.**
인수 테스트가 두 경로를 모두 고정한다.

## E. 진행 상태

B-1~B-5는 위 B절로 **모두 확정**됐다. 남은 블로킹 결정은 없다.

구현 중 확인된, 검토 시 예상과 달랐던 점:

1. **B-1은 한 줄 추가로 끝나지 않는다.** 불변식 7과 8을 동시에 만족시키려면
   유예 분기와 함께 유예 전용 종료 판정이 필요하다 (B-1절 참조).
2. **2단계 테마 해금이 비어 있었다.** `processUnlocks`에 `secondTheme` 부여 조건이
   아예 없어서, 단계만 2로 올라가고 해금은 일어나지 않았다.
   전환 코드가 직접 부여하지 않고 `stage >= 2` 조건으로 판정하도록 넣었다.
   기존 ID 검사가 중복 부여를 막는다.
3. **`migrateV3ToV4`가 체인의 최종 단계가 아니게 됐다.** v4에서 곧바로
   현재 `RULES_VERSION`을 쓰던 코드를 v4 시절 값(`economy-0.2+b3-emergency`)으로 바꿨다.
   그래야 다음 단계 `migrateV4ToV5`가 (saveVersion, rulesVersion) 조합을 다시 검사한다.

중규모 대회(P15)는 C-1에서 완료로 표시하지 않는다.
