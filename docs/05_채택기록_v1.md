# 채택 기록 v1 — 경제 엔진 1차

작성일: 2026-09-19. 근거: 사용자 결정 (검토 보고 4장에 대한 회신).

이 문서는 `04 §4`가 요구한 "구현 전에 채택 여부를 기록할 신규 제안" 목록의 실제 기록이다.
`01 GDD v1.0`의 확정 원칙은 이 문서로 변경되지 않는다. 이 문서가 바꾸는 것은
`02 Economy v0.1` / `03 Progression v0.1`의 **초안 항목 중 무엇을 이번 코드가 따르는가**뿐이다.

표기 규칙:

- **확정** — GDD v1.0에서 확정된 사항. 코드가 반드시 따른다.
- **채택** — 초안 중 이번 구현이 따르기로 한 것. `config/economy.ts`에서 변경 가능.
- **보류** — 이번 구현이 판단하지 않은 것. 코드에 임의 기본값을 넣지 않는다.
- **후속** — 다음 작업으로 미룬 것. 자료구조 자리만 있거나 아예 없다.

### 1-1. 중규모 대회의 확정도 통일

세 문서가 같은 항목을 서로 다른 강도로 서술하고 있었다. 아래로 통일한다.

> **중규모 대회는 "첫 플레이 가능한 완성본"의 포함 범위다. 이번 경제 엔진 작업의 범위는 아니다.**

- `01 GDD §8`의 "중규모 토너먼트 해금"은 2단계의 확정 해금 항목이다. 변경 없음.
- `03 Progression §1`의 "실제 개최할 수 있어야 한다"는 **첫 완성본의 인수 기준으로 유지**한다. (`03 P15`)
- `04 §4`가 이를 "신규 제안"으로 분류한 것은 **밸런스 수치(4테이블·4딜러·참가비·상금)가 미검증**이라는 뜻으로 한정한다. 기능 포함 여부는 제안이 아니라 포함 확정이다.
- 이번 엔진 작업에는 구현하지 않는다. → **작업 C-2에서 구현했다 (7-6).**
  밸런스 수치는 여전히 미검증 제안이며, 현행 config 값을 잠정 기준으로 쓴다.

`03`과 `04`의 해당 문장에 이 구분을 반영했다.

### 2-1. R9에 대한 이번 구현의 실제 동작

대회가 없으므로 대회용 직원 선택 코드 자체가 없다. 다만 인접한 곳에서 같은 원칙을 지켰다.

- `buyTable`은 **대기(standby) 상태의 일반 딜러만** 자동 배치한다 (`03 §7`). 다른 테이블에 배치된 딜러는 절대 건드리지 않는다.
- `assignDealer`는 대상 딜러가 이미 다른 테이블에 배치·예약돼 있으면 **거절**한다 (`02 §5` 중복 배치 금지).

### 2-2. R9 확정 — 대회 예약의 테이블·딜러 선택 정책 (작업 B-1)

> **플레이어가 예약할 테이블 ID를 직접 고른다. 딜러는 선택된 테이블의 현재 담당자다.**

- 소규모 대회는 테이블 2개·딜러 2명을 요구한다 (`02 §8`). 명령은 `tableIds` 2개만 받는다.
- 딜러 ID는 **선택된 테이블에서 파생**한다. 명령이 딜러를 따로 지정하지 않는다.
- **자동 선택은 없다.** 다른 운영 테이블의 딜러를 빼오지 않고, 대기 직원을 자동 배치하지도 않는다.
- 대기 딜러를 쓰고 싶으면 예약 **전에** 기존 `assignDealer`로 테이블에 배치해야 한다.
- 선택 가능한 테이블의 조건: 매장에 존재 / `operating` / 근무 중 담당 딜러 보유 /
  대기 중인 딜러 변경 없음 / 다른 대회·리모델링 예약 없음. 테이블 ID와 딜러 ID 모두 중복 불가.
- 예약된 딜러는 `assignDealer`·`setStaffStandby`로 풀 수 없고, 예약 테이블은
  `assignDealer`·`unassignDealer` 대상이 아니다. 자원 해제는 작업 B-2의 대회 종료만 할 수 있다.

**테이블 상태의 소유권 분리.** `closing`(딜러 변경 대기)과 `tournamentHeld`(대회 점유)는
둘 다 신규 착석을 막지만 소유자가 다르다. `applyPendingDealerChanges`는 `closing`만 처리하며
`tournamentHeld`를 절대 건드리지 않는다. 이 분리가 깨지면 예약된 딜러가 조용히 풀린다.

### 2-3. R10 채택 — 대회 운영 예비금 4게임시간 (잠정 밸런스)

**채택 규칙**

```text
예약 자격 = 사용 가능 현금 >= 준비비 + 현재 시간당 운영비 x 4
```

- **필수 예약 자격 조건이다.** 경고가 아니라 거절 사유다 (`TOURNAMENT_RESERVE_SHORTFALL`).
- 경계는 정확하다. 필요 금액과 **같으면 통과**, 내부 화폐 단위로 **1 모자라면 거절**한다.
- 시간당 운영비는 기존 `minuteCosts x 60` 파생값(`hourlyOperatingCostUnits`) 하나만 쓴다.
  두 번째 비용 계산을 만들지 않는다.
- **예비금은 잠기지 않는다.** 예약이 잠그는 금액은 준비비뿐이고,
  예비금은 사용 가능 현금으로 남아 이후 운영비로 소진된다.

**적용 범위는 대회 예약뿐이다.**

| 규칙 | 상태 |
|---|---|
| 대회 예약 예비금 | **R10으로 채택.** 4게임시간, 필수 |
| 일반 구매의 4게임시간 (`03 §3`) | **변경 없음.** 경고일 뿐 구매를 막지 않는다 |
| 리모델링 `4 x C_after` (`03 §5`) | **변경 없음.** 리모델링 전용 공식 |

**잠정 밸런스다.** `02 §8`·`03 §3`이 검사를 필수로 지정했지만 수치는 없었고,
이 값은 그 빈자리를 메우기 위해 정한 것이다. `03 §3`의 일반 구매 경고와
`03 §5`의 리모델링 예비금이 모두 4게임시간을 쓰는 것과 일관되게 맞췄다.
플레이 테스트로 조정할 대상이며, `config.tournamentOperatingReserveHours`
한 줄만 바꾸면 된다. `null`로 두면 예비금 항을 요구하지 않는 이전 동작이 된다.

**관측된 의미.** 매출이 전혀 없는 구성(예약 테이블 2개가 영업 테이블 전부인 경우)에서
예비금은 정확히 **240게임분 = 4게임시간**을 버티고, 그다음 분에 엔진이
`EMERGENCY_NOT_IMPLEMENTED`로 명시적으로 멈춘다. 잠긴 준비비는 잠식되지 않는다.

## 3. 현금과 잠금 금액

| 용어 | 정의 |
|---|---|
| `cash` | **잠긴 금액을 포함한 총보유현금** |
| `lockedCash` | `cash` 중 사용할 수 없는 금액 |
| 사용 가능 현금 | `cash - lockedCash`. 모든 구매·고용 가능 판정은 이 값을 쓴다 |

처리 규칙:

1. **예약** — `lockedCash`만 증가. `cash`는 변하지 않는다.
2. **정산** — `cash` 감소와 `lockedCash` 감소를 **각각 한 번씩** 처리한다.
3. **해제(취소)** — `lockedCash`만 감소. `cash`는 변하지 않는다.

불변식(매 틱 검사):

```
0 <= lockedCash <= cash        (잠금이 보유액을 넘을 수 없다)
availableCash = cash - lockedCash
```

`02 §7`의 "예약 즉시 비용 처리"(검산 도구)와 이 잠금 방식은 **보고 화면의 시점이 다를 뿐**,
같은 준비비와 같은 사용 가능 현금을 적용하면 구매 가능 시점이 반드시 달라지지는 않는다.
검산 결과와의 차이가 생기면 그때 원인을 분리해 기록한다.

## 4. 숫자 표현과 재현성

### 4-1. 화폐

**1G = 60 내부 단위(units)로 채택한다.** 모든 반복 비용이 "게임 시간당 정수 G"로 정의되고
틱이 게임 1분이므로 다음 항등식이 성립한다.

```
분당 차감 units = (시간당 비용 G) × 60 / 60 = (시간당 비용 G)
```

즉 80G/시간 → 정확히 80 units/분. 나눗셈도 반올림도 발생하지 않는다.

- 안전 범위: 가장 비싼 항목인 18번째 테이블 286,800G = 17,208,000 units.
  `Number.MAX_SAFE_INTEGER`(9.007×10^15) 대비 8자리 여유. 엔진이 매 틱 상한을 검사한다.
- 모든 금액은 정수다. 비정수 금액이 만들어지면 즉시 예외를 던진다.

**향후 할인·비율 비용의 반올림 규칙 (선결정, 이번 구현에는 해당 항목 없음)**

1. 비율 연산은 항상 **내부 units 정수 위에서** 수행한다. G로 환산한 뒤 곱하지 않는다.
2. 결과는 **내림(floor)** 하고, 버린 나머지는 해당 항목의 carry에 **보존**한다.
   carry를 둘 수 없는 일회성 금액은 내림하고 버린다.
3. 어떤 경우에도 `Math.round`의 은행가 반올림/대칭 반올림 혼용을 하지 않는다.
   이유: 음수 금액(환불)에서 `round`와 `floor`의 부호 거동이 갈려 재현성이 깨진다.
4. 이 규칙을 바꾸면 `rulesVersion`을 올린다.

### 4-2. 인지도·만족도

**×1000 정수(milli 단위)로 채택한다.** 인지도 0~100,000 / 만족도 40,000~95,000.

- 인지도 증가값은 모두 정수로 떨어진다. 세션 +0.02 → **+20**, 대회 +12/+18 → **+12,000/+18,000**, 홍보 +5 → **+5,000**. 반올림이 없다.
- **만족도는 반올림으로 버리지 않는다.** 감쇠식을 정수 분수로 계산하고 나머지를 상태에 보존한다.

```
k  = 1 - exp(-1/360)                       (Δ = 게임 1분, 시상수 6게임시간)
k ≈ 0.0027739233228...
SAT_K_NUM = 2773923,  SAT_K_DEN = 1000000000        (k를 10^-9 자리까지 고정)

total = (T_milli - S_milli) × SAT_K_NUM + satisfactionRemainder
step  = floor(total / SAT_K_DEN)
satisfactionRemainder = total - step × SAT_K_DEN     (항상 0 이상 SAT_K_DEN 미만)
S_milli += step
```

내림 + 나머지 보존이므로 누적 오차는 **영구히 1 milli(=0.001) 미만**이다.
음수 변화에도 floor를 쓰므로 부호에 따라 거동이 갈리지 않는다.
`satisfactionRemainder`는 **저장·복원 대상**이다.

### 4-3. 방문 수요 누적값

부동소수를 쓰지 않는다. 공식 전체를 하나의 정수 분수로 계산한다.

```
D = B × (1 + A/10) × (0.75 + 0.5 × S/100)          (게임 1시간당 명)
분당 증가분 = D / 60

ARRIVAL_NUM = baseDemandMilli × (10000 + awarenessMilli) × (150000 + satisfactionMilli)
ARRIVAL_DEN = 1000 × 10000 × 200000 × 60 = 1.2 × 10^14

total       = ARRIVAL_NUM + arrivalCarry
newGuests   = floor(total / ARRIVAL_DEN)
arrivalCarry = total - newGuests × ARRIVAL_DEN       (0 이상 ARRIVAL_DEN 미만)
```

- 검증: 초기값 B=3.5, A=0, S=80 → NUM = 3500 × 10000 × 230000 = 8.05×10^12,
  분당 8.05×10^12 / 1.2×10^14 = 0.0670833... → 시간당 **4.025명**. 문서 값과 일치.
- 최댓값 검사: NUM 최대 6000 × 110000 × 245000 = 1.617×10^14, `total` 최대 약 2.82×10^14.
  안전 정수 범위 대비 충분하다.
- `arrivalCarry`는 **저장·복원 대상**이다.

### 4-4. 서비스 품질과 목표 만족도의 반올림

```
Q_milli = min(100000, floor(100000 × 서비스수용기준 / max(8, O)))
qTerm   = floor(15 × (Q_milli - 100000) / 100)              // 0.15 × (Q - 100)
lTerm   = (윈도우 방문수 == 0) ? 0 : floor(10000 × 이탈수 / 방문수)   // 10 × L
T_milli = clamp(80000 + 3000 × 편의시설레벨 + qTerm - lTerm, 40000, 95000)
```

T는 **목표값**이며 S가 그쪽으로 수렴한다. 각 항의 내림 오차는 최대 1 milli(0.001)이고
S의 변화량 자체는 4-2의 나머지 보존으로 손실되지 않는다.

### 4-5. 결정론의 검증 방법

**고정 상수를 썼다는 사실만으로 결정론이 확보됐다고 보지 않는다.** 다음 두 테스트로 확인한다.

1. **시간 분할** — 1,440분 1회 진행과 60분씩 24회 진행의 **상태 전체**가 같아야 한다.
   (부분 필드 비교가 아니라 직렬화 결과 전체 비교)
2. **저장 복원** — 임의 시점에 직렬화 → 역직렬화 → 이어서 진행한 결과가
   중단 없이 진행한 결과와 **상태 전체**가 같아야 한다.
   나머지 값(`arrivalCarry`, `satisfactionRemainder`, 이탈률 윈도우)이 빠지면 이 테스트가 깨진다.

## 7. 버전 관리

| 필드 | 의미 | 변경 시점 |
|---|---|---|
| `rulesVersion` | 계산 순서·공식·반올림 규칙 | `02 §10` 처리 순서, 4장의 정밀도 규칙, 공식이 바뀔 때 |
| `saveVersion` | 직렬화 스키마 | 상태 필드가 추가·삭제·개명될 때 |

둘은 독립적으로 올린다. 밸런스 **수치**만 바뀌는 경우에는 어느 쪽도 올리지 않는다
(`04 §4` "매번 기획 전체를 바꾸지 않고 데이터로 조정").

현재 값: `rulesVersion = "economy-0.3+c1-remodel"`, `saveVersion = 5`.

**작업 B-1의 버전 판정**

- `rulesVersion` — **올리지 않았다.** 대회 예약은 상태를 추가했을 뿐 수요·착석·만족도·매출·비용의
  공식과 `02 §10`의 9단계 순서를 바꾸지 않았다. 3단계는 문서가 대회용으로 비워 둔 자리이며,
  예약이 없는 상태(`tournament === null`)의 계산 결과는 이전과 완전히 같다.
  기존 시간 분할·저장 복원·검산 재현 테스트가 이를 검증한다.
- `saveVersion` — **1 → 2.** `GameState.tournament`가 예약 레코드를 담을 수 있게 되었고
  `records.nextTournamentSeq`가 추가됐다. `§7`의 "상태 필드가 추가될 때"에 해당한다.
  v1 저장본은 예약을 표현할 수 없었으므로 마이그레이션 의미가 완전히 정의된다
  (`tournament: null` 유지, `nextTournamentSeq = 1`). 정의되지 않은 버전은 거절한다.

**작업 B-2A의 버전 판정**

- `rulesVersion` — **올리지 않았다.** 대회 진행·정산은 `02 §8`이 이미 규정한 동작을
  구현한 것이고, 수요·착석·만족도·일반 매출·비용의 공식과 `02 §10`의 9단계 순서를
  바꾸지 않았다. 대회가 없는 상태의 계산 결과는 이전과 완전히 같다.
**작업 B-3의 버전 판정**

- `rulesVersion` — **올렸다** (`economy-0.1+adopt-v1` → `economy-0.2+b3-emergency`).
  8단계가 "비용 확정 → 부족액 지원 → 1회 차감"으로 바뀌었고, 긴급 운영 중 신규 착석이
  유지 대상 하나로 제한되며, 9단계가 긴급 축소와 기존 배치 전환 중 하나를 고르게 됐다.
  자금이 마르지 않는 상태의 결과는 이전과 같지만 규칙 자체가 달라졌다.
- `saveVersion` — **3 → 4.** `GameState.emergency`와
  `records.totalEmergencySupportUnits` / `emergencyMinutes` / `nextEmergencySeq`가 추가됐다.
  v3 → v4 마이그레이션은 의미가 완전히 정의된다: v3은 긴급 운영을 표현할 수 없었으므로
  `emergency = null`, 지원금 누계 0, 긴급 분 0, 시퀀스 1이 유일하게 옳은 값이다.
  완료된 대회 기록·준비비 잠금·직원 보상 기록·나머지 누계는 그대로 보존한다.
  v3 저장본에 긴급 상태가 들어 있으면 거절한다. 손상된 데이터를 지원금으로 정상화하지 않는다.

  **필수 필드.** `tournament` / `remodel` / `emergency`는 작업 A(saveVersion 1)부터
  모든 저장본에 직렬화됐다. **값이 null인 것과 필드가 누락된 것은 다르다.**
  어느 마이그레이션도 이 필드를 초기화하지 않으며, 없으면 버전 분기 전에 거절한다.
  누락을 null로 복구하면 대회 예약이 사라진 채 준비비 잠금과 `tournamentHeld`
  테이블만 남은 상태가 정상으로 세탁된다.
  각 버전의 마이그레이션은 **그 버전에 실제로 없던 필드만** 초기화한다.

  | 버전에서 추가 | 필드 |
  |---|---|
  | v2 | `records.nextTournamentSeq` |
  | v3 | 예약의 `startedAtMinute`·`endsAtMinute`, `records.totalTournamentRevenueUnits`·`completedTournaments` |
  | v4 | `records.totalEmergencySupportUnits`·`emergencyMinutes`·`nextEmergencySeq` |
  | v5 | `records.completedRemodels`·`nextRemodelSeq` |

  검사 지점은 `deserialize`(마이그레이션 진입부), `tick` 진입부, `cloneState` 세 곳이다.
  `cloneState`가 누락을 null로 바꾸지 않으므로 복제 경로로 우회할 수 없다.

  **원본 조합 검사.** 마이그레이션은 (저장 구조 버전, 계산 규칙 버전) **조합**을 본다.
  작업 A부터 B-2C까지 규칙 버전은 `economy-0.1+adopt-v1` 하나였고 B-3에서
  saveVersion 4와 함께 올라갔으므로, `saveVersion <= 3`과 함께 실제로 존재한 조합은
  그 하나뿐이다. 다른 규칙 버전이 붙은 v1~v3 저장본은 **거절한다.**
  규칙 버전을 무조건 현재 값으로 덮어써서 알 수 없는 저장본을 받아들이지 않는다.

- `saveVersion` — **2 → 3.** 다음 상태 필드가 추가됐다.
  `TournamentReservation.startedAtMinute` / `endsAtMinute`,
  `records.totalTournamentRevenueUnits`, `records.completedTournaments`.
  v2 → v3 마이그레이션은 의미가 완전히 정의된다: v2가 담을 수 있던 대회 상태는
  "없음 / RESERVED_DRAINING / RESERVED_READY"뿐이고, 시작 시각은 `null`이 유일하게
  옳은 값이며, 참가비 누계는 0, 완료 기록은 빈 목록이다. 예약 테이블·딜러 ID,
  잠긴 금액, 소비한 개최권은 건드리지 않는다. v2가 표현할 수 없는 단계는 거절한다.

**작업 C-1의 버전 판정**

- `rulesVersion` — **올렸다** (`economy-0.2+b3-emergency` → `economy-0.3+c1-remodel`).
  리모델링이 걸린 동안 5단계의 신규 방문 생성이 멈추고(누적 잔여도 동결), 6단계의
  신규 착석이 막히며, 7단계의 만족도 갱신이 고정되고, 9단계에 전환 처리가 추가됐다.
  긴급 운영의 축소 시점도 달라진다. 리모델링이 없는 상태(`remodel === null`)의
  계산 결과는 이전과 완전히 같지만, 규칙 자체가 달라졌으므로 올린다.
- `saveVersion` — **4 → 5.** `records.completedRemodels`와 `records.nextRemodelSeq`가
  추가됐다. v4 → v5 마이그레이션은 의미가 완전히 정의된다: v4는 리모델링 작업을
  표현할 수 없었으므로 완료 기록은 빈 목록, 시퀀스는 1이 유일하게 옳은 값이다.
  `remodel` 필드 자체는 작업 A(v1)부터 늘 있었으므로 **초기화하지 않고 값만 확인**한다.
  v4 저장본에 리모델링 작업이 들어 있으면 거절한다.
  완료된 대회 기록·준비비 잠금·직원 보상 기록·긴급 운영 누계·나머지 누계는 그대로 보존한다.

  **체인의 중간 단계도 조합을 검사한다.** v3 → v4는 더 이상 체인의 마지막이 아니므로,
  현재 `RULES_VERSION`이 아니라 **v4 시절의 값**(`economy-0.2+b3-emergency`)으로 올린다.
  그래야 다음 단계인 v4 → v5가 (saveVersion 4, rulesVersion) 조합을 다시 검사한다.
  중간 단계가 현재 값을 미리 써 버리면 알 수 없는 조합이 검사를 통과한다.

**작업 C-2의 버전 판정**

- `rulesVersion` — **올리지 않았다.** B-2A와 같은 이유다. 중규모 대회는 `02 §8`이 이미
  규정한 동작을 연결한 것이고, 수요·착석·만족도·일반 매출·비용의 공식과 반올림,
  `02 §10`의 9단계 순서를 바꾸지 않았다. 3단계의 대회 처리 코드는 한 줄도 바뀌지 않았다
  (B-2A부터 `config.tournament[scale]`만 참조했다). 9단계에 늘어난 것은 조건 판정식
  해금 하나이며, 같은 종류의 추가였던 B-2B도 올리지 않았다.
  중규모 대회가 없는 상태의 계산 결과는 이전과 완전히 같다 (기존 414건 무변경 통과).
- `saveVersion` — **올리지 않았다 (5 유지).** 새 영속 필드가 없다.
  `TournamentReservation.scale`과 `completedTournaments[].scale`은 v2/v3부터
  `'small' | 'mid'`였고, 해금 표시 `midTournament`는 기존 `unlocks` 배열에 담는다 (7-2와 같은 방식).
  C-2 이전에 2단계가 된 v5 저장본은 **마이그레이션 없이** 읽히고, 조건을 해금 기록이 아니라
  상태(단계)에서 직접 보므로 다음 틱에 정확히 한 번 해금된다. 그 밖의 상태는 1바이트도 달라지지 않는다.

### 7-6. 중규모 대회 (C-2)

**수치는 잠정 기준이다.** `02 §8`의 중규모 값(테이블·딜러 각 4, 참가자 16~32,
`min(32, floor(D × 3))`, 360게임분, 참가비 240G, 상금 100G, 운영비 30G, 개최비 1,800G,
인지도 +18)은 검산을 거치지 않은 제안이다. 대안 수치가 문서에 없고 이미 `config.tournament.mid`에
들어 있었으므로 **상수를 바꾸지 않고 그대로 쓴다.** 조정은 config 한 곳에서 한다.

**엔진에 규모별 분기를 만들지 않았다.** 자격 판정을 `planTournament(state, scale, …)`로
일반화했고 소규모 공개 이름(`planSmallTournament`, `forecastSmallTournament`,
`reserveSmallTournament`)은 그대로 유지했다. 검사 12개의 항목과 순서는 규모와 무관하게 같다.
R2(준비비 구성)·R3(예약된 전문 딜러 1.25, 중첩 없음)·R4(인지도 상한)·R9(테이블 명시 선택)·
R10(운영 예비금 4게임시간)과 "게임일당 개최권 1회, 규모 공유"가 그대로 적용된다.

**해금과 실행 가능 여부를 분리한다 (`03 §4`).** 해금 조건은 "2단계 도달" 하나다.
1단계에서는 `TOURNAMENT_LOCKED`로, 해금 뒤 자원이 모자라면 부족한 항목의 사유
(`TOURNAMENT_TABLE_COUNT`·`TOURNAMENT_TABLE_NOT_OPERATING` 등)로 거절한다.

**참가자 수는 전제가 아니라 결과다.** `D`는 **예약 시점의 현재 시간당 방문 수요**
(`demandPerHourMilli`: 단계 기본값 × 인지도 × 만족도)이고 참가자는 예약 때 한 번 확정된다.
16명에 못 미치면 `TOURNAMENT_PARTICIPANTS_TOO_FEW`로 거절하며 상태를 바꾸지 않는다.
인지도가 줄어드는 경로가 없으므로 자연 수요의 2단계 최저값은 인지도 0·만족도 40의
5.7명/시간 → 17명이고, 리모델링을 실제로 거친 매장(인지도 50 이상)은 32명이 된다.
그래도 32명을 상수로 취급하지 않는다. 테스트는 15(거절)·16·17·24·32명을 각각 만든다.

**손익은 참가자 수의 함수다.** 기존 `tournamentPrepCostUnits`와 참가비 공식을 그대로 쓴다.

| 참가자 | 준비비 | 참가비 | 대회 자체 순익 |
|---:|---:|---:|---:|
| 16 | 3,880G | 3,840G | **−40G** |
| 17 | 4,010G | 4,080G | +70G |
| 24 | 4,920G | 5,760G | +840G |
| 32 | 5,960G | 7,680G | +1,720G |

최소 인원에서는 대회 자체만으로 적자다. 현행 수치의 결과이며 이번에 고치지 않는다.

**중규모 완료는 새 보상을 만들지 않는다.** 대회 전문 딜러 지급 조건은 "소규모 1회"(`02 §5`)이고,
리모델링 조건도 소규모 완료만 센다 (`03 §5`). 둘 다 기존 `scale === 'small'` 판정 그대로다.

**예상치.** `forecastTournament(state, scale, tableIds, …)`가 두 규모를 같은 방식으로 비교한다.
일반 `forecast()`는 중규모 예약 명령도 `TOURNAMENT_NOT_IMPLEMENTED`로 돌려보낸다.
이 분기를 빠뜨리면 일반 투자 회계가 준비비 잠금과 지연 정산을 잘못 계산한 채
`supported: true`를 돌려주게 된다.

**`assertSupported`의 규모 관문.** "소규모만 지원" 검사는 미구현 표시였다.
두 규모를 허용하되 **정의되지 않은 규모는 계속 거절한다** — `config.tournament[scale]` 조회가
`undefined`를 돌려줘 계산이 조용히 깨지기 때문이다.

**성장 시뮬레이션 (`npm run simulate`).** 위 6장의 후속 과제 세 가지를 **측정만** 했다.
가상 플레이어는 `04 §2`의 자동 투자 정책을 따른 가정이며 게임 규칙이 아니다.
시간표는 실제 플레이 시간의 보장이 아니다. 수치는 하나도 바꾸지 않았다.

**세 경로의 차이는 2단계 대회 정책뿐이다.** 시나리오 A의 이름은 "대회 없음"이 아니라
**"2단계 대회 없음"**이다. 세 경로 모두 1단계에서 **소규모 대회 2회를 완료한다**
(리모델링 필수 조건이다). 정책 인자는 `venue.stage === 2`일 때만 읽히므로
1단계 구간은 정책과 무관하다.

검증 결과 세 경로는 같은 지점에서 출발한다.

| 대조 항목 | 결과 |

| 초기 상태(0분) 직렬화 | 3경로 동일 |
| 1단계 명령 시퀀스 26건 | 3경로 동일 |
| 1단계 소규모 대회 2회 | 3경로 동일 (`TN1` 게임일 0 / 16명 / 956–1196분, `TN2` 게임일 1 / 16명 / 1533–1773분) |

`TN2`가 이미 썼고 리모델링도 같은 게임일에 끝나므로, 2단계 첫 대회는 게임일 2부터 가능하다.

**지연 비율은 리모델링 완료 후 기준으로 읽는다.** 1단계 38.0게임시간이 3경로 모두
동일한 프리픽스이므로, 게임 시작 기준 절대값으로 비율을 내면 과소평가된다.
소규모 +2.2% / 중규모 +10.1%가 실제 지연이며, 절대값 기준의 +1.7% / +8.0%가 아니다.

**이탈률 차이는 두 효과가 합쳐진 값이다.** 하나는 대회가 테이블을 점유해 처리 능력이
줄어드는 직접 효과이고, 다른 하나는 대회 인지도 보상이 수요를 끌어올리는 간접 효과다.
인지도 100 도달 시점이 대회를 여는 쪽에서 15게임시간가량 빠르다

따라서 위 이탈률 차이를 테이블 점유 효과만의 크기로 읽으면 과대평가된다.

대회 기회비용. **같은 상태에서 분기해 "연다 / 안 연다"를 각각 24게임시간 진행한 쌍 비교다**
(`forecastTournament`). 두 분기가 같은 시점·같은 상태에서 출발하므로 위와 달리
인지도 누적 차이가 개입하지 않는다. 참가자 상한 기준이다.

| 운영 테이블 | 규모 | 대회 순익 | 일반 매출 차이 | 현금 차이 | 인지도 |
|---:|---|---:|---:|---:|---:|
| 8 | 소 | +1,000G | −6,400G | −5,400G | +12 |
| 8 | 중 | +1,720G | −19,200G | −17,480G | +18 |

| 10 이상 | 중 | +1,720G | −25,600G | −23,880G | +18 → 0 |

수요가 처리 능력을 넘는 2단계에서는 대회가 점유한 테이블만큼 일반 매출이 그대로 빠진다.
−25,600G는 테이블 4개 × 시간당 4명 × 200G × 8게임시간(정리 최대 2시간 + 진행 6시간)이다.

대회를 열 동기가 현금으로도 인지도로도 남지 않는다. **밸런스 과제로 남긴다.**

### 7-5. 첫 리모델링 (C-1)

1단계 → 2단계 전환. 결정 내역과 인수 조건은 `06_리모델링_구현규칙_C1.md`에 있다.
여기에는 **엔진 불변식으로 굳힌 것**만 적는다.

**비용의 1회성.** 요청 시 15,000G를 잠그고(`lockedCash`만 증가), 전환 시
`settleLocked`로 `cash`와 `lockedCash`를 한 번에 줄인다. 잠금과 정산 사이에
그 돈은 `availableCash`에서 빠져 있으므로 일반 운영비로도, 긴급 지원 계산에도
섞이지 않는다. `completedRemodels`에 기록이 남아 재정산을 막는다.

**요청의 원자성.** `planRemodel`은 상태를 바꾸지 않고 자격만 판정한다.
`applyRemodelRequest`에서 던질 수 있는 호출은 잠금 하나뿐이고 그것이 맨 앞에 온다.
잠금이 실패하면 이후 변경이 시작되지 않는다. `tick`이 입력 상태를 복제하므로
그 위의 어떤 실패도 호출자 상태를 더럽히지 않는다.

**보존.** 전환은 `venue.stage`만 바꾼다. 테이블·직원 배열을 다시 만들지 않으므로
ID·자산·배치가 그대로 남고, 완료 기록에 전환 시점의 `preservedTableIds` /
`preservedStaffIds`를 함께 적어 사후 검증이 가능하다.
특별 직원 지급 기록, 대회 완료 기록, 개최권, 인지도, 게임 시각은 건드리지 않는다.

**통계에 허위 기록을 넣지 않는다.** 공사로 해산한 대기 손님은 `arrivals`에도
`abandons`에도 넣지 않는다. 대신 공사 중에도 `recordWindow(0, 0)`를 매 분 호출한다.
윈도우를 멈추는 것이 아니라 **실제로 방문 0, 이탈 0이었다는 사실을 기록**하는 것이다.

**2단계 수요의 적용 시점.** 전환은 9단계에서 일어나고 수요는 5단계에서 계산되므로,
`stage = 2` 수요는 **완료 다음 게임 분부터** 반영된다. 2단계 수요 설정값은
이번 작업에서 바꾸지 않았다. 전환 직후의 높은 이탈률은 현재 밸런스의 결과이며
`§6`의 미해결 과제로 계속 남는다.

**긴급 운영과의 관계 (B-1 결정 ①).** 공사 중에도 부족액 지원은 B-3대로 정상 처리하고
**테이블·딜러 축소만 유예**한다. 유예 중 종료 판정은 B-3와 **같은 잣대**를 쓴다 —
B-3의 자금 조건이 "축소 완료 상태의 분당 반복 비용 × 240"이므로, 유예 중에도
*축소했다면 남았을 배치*(유지 테이블 1개 + 담당 딜러 1명 + 매장 기본비)로 기준액을 만든다.
현재(축소 전) 배치로 재면 기준액이 실제 B-3보다 커져, 공사 중 이미 회복된 매장까지
완료 다음 분에 1테이블로 줄였다가 같은 틱에서 종료하게 된다. 그 불필요한 축소를 막는다.
`processRemodel`은 9단계의 **마지막**에 둔다. 그래야 완료된 분에는 긴급 상태가 그대로 남고,
유예된 축소는 다음 분의 정상 B-3 경로가 처리한다.
새 밸런스 상수는 만들지 않았다. 급여·시설비·매장 기본비와 `perMinuteUnits`만 쓴다.

**거절 사유 두 가지를 구분한다.**

| 사유 | 의미 | 발생 지점 |
|---|---|---|
| `REMODEL_ACTIVE` | 공사 중이라 **지금 이 명령을 실행할 수 없다** | `commands.ts` 공통 관문 |
| `REMODEL_IN_PROGRESS` | **대회를 열 수 없다** (대회 자격 판정의 결론) | `tournament.ts`의 `planSmallTournament` |

공통 관문이 생겼다고 해서 대회 자격 판정의 사유를 지우지 않는다. 둘 다 유지한다.

**예상치.** 리모델링이 걸린 상태와 `requestRemodel` 명령은 `forecast` 계열에서
`REMODEL_NOT_IMPLEMENTED`로 **명시적 미지원**을 돌려준다. 공사 중에는 신규 방문이 멈추고
비용이 잠겨 있다가 전환 시 지출되므로, 일반 투자 회계 필드로는 현금흐름을 옳게 표현할 수 없다.
`§8`의 원칙대로 그럴듯한 숫자를 지어내지 않는다. 전용 예상치는 후속 작업이다.

### 7-4. 긴급 축소 운영 (B-3)

**발동과 지급 (8단계).** 순서가 규칙이다.

```text
1. 현재 배치로 이번 분의 반복 비용 C를 한 번 계산한다
2. 사용 가능 현금 A = cash - lockedCash
3. A < C 이면 긴급 운영에 진입한다 (A = C 이면 진입하지 않는다)
4. 부족액 S = max(0, C - A) 만 지원한다
5. 확정한 C를 한 번 차감한다
```

지원은 `cash`만 늘리고 `lockedCash`는 건드리지 않는다. 잠긴 준비비를 운영비로
쓰지 않으며, 현금을 조용히 0으로 자르지도 않는다.

불변식 `0 <= lockedCash <= cash`는 두 경로 모두에서 성립한다.

| 경우 | 차감 후 |
|---|---|
| A >= C (지원 없음) | `cash' = cash - C >= lockedCash` |
| A < C (부족액 지원) | `cash' = lockedCash` |

`cash === lockedCash`는 **부족액을 지원해 비용을 낸 분의 결과**이며,
모든 정상 틱에서 성립하는 등식이 아니다.

**입력 무결성 관문.** 정상적인 "이번 분 비용 부족"과 이미 손상된 입력 상태는 다르다.
`assertCashIntegrity`가 `cash < 0`, `lockedCash < 0`, `lockedCash > cash`를
**지원금 지급이나 같은 분 매출이 가리기 전에** 거절한다. `tick` 진입 시점(복제 전,
따라서 거절해도 원본 불변)과 `deserialize` 양쪽에서 검사한다.
잔액 0, 비용과 같은 잔액, 비용보다 1unit 부족한 잔액은 모두 `cash >= 0`이므로
이 관문을 통과하고 정상적으로 지원받는다.

발동한 분의 비용을 줄이려고 배치를 소급 변경하지 않는다. 축소는 9단계에서 적용되고
절감은 다음 분부터 나타난다. 복구 목표액을 일괄 충전하지 않으며, 구매·고용·홍보·
신규 대회 준비비는 지원 대상이 아니다. 상환 의무도 없다.

**계정 분리.** 지원금은 `records.totalEmergencySupportUnits`와 원장 유형
`emergencySupport`로만 기록한다. 매출·대회 매출·영업 순이익·일회성 구매 비용에
섞지 않는다. 거래는 `emergency:<ID>:support`로 식별한다.

**유지 대상 선택 (9단계).** 후보는 두 종류다.

| 후보 | 조건 |
|---|---|
| A | 대회에 예약되지 않은 테이블과 **현재 담당 딜러**. 기존 세션이 있어도 된다 |
| B | 일반 세션이 없는 미운영 테이블과 다른 업무에 묶이지 않은 대기 딜러 |

진행 중인 세션의 담당자를 다른 테이블로 빼오는 조합은 만들지 않는다.
우선순위는 ① 시간당 유지비 ② 기존 근무 배치 유지 ③ 작은 `spotIndex`
④ 직원 ID 사전순이다. 전순서이므로 같은 상태에서 항상 같은 조합이 나온다.
한 번 고르면 끝까지 유지하며 매분 더 좋은 조합으로 교체하지 않는다.
가능한 조합이 없으면 대상을 비워 두고 매분 다시 확인한다. 직원을 새로 만들지 않는다.

**예약 해제가 선택보다 먼저다.** 9단계는 ① 일반 딜러 교체 예약 해제 →
② 서비스 직원 대기 전환 → ③ 유지 대상 선택 → ④ 활성화 → ⑤ 나머지 정리 →
⑥ 종료 판정 순서로 실행한다. 해제를 선택 뒤에 두면 곧 취소될 예약에 묶인 대기
딜러가 후보에서 빠져, 더 저렴한 조합을 두고 비싼 조합을 고르게 된다.
대회 예약 테이블은 이 해제 대상이 아니다.

**축소와 자원 소유.** 유지 대상 밖의 일반 테이블은 신규 착석을 막고 기존 세션만
정상 완료한다. 마지막 세션이 정산되면 같은 분의 9단계에 미운영으로, 담당 딜러는
대기로 바꾼다. 서비스 직원은 발동한 분에 대기로 전환한다. 아직 투입되지 않은
`pendingDealerId` 예약은 해제하고, 긴급 운영 중에는 축소 계획이 기존 배치 전환
처리를 **대신한다**(두 소유자가 같은 테이블을 동시에 건드리지 않는다).

대회 예약 자원은 별개다. DRAINING·READY·IN_PROGRESS 모두 기존 흐름을 계속하며,
긴급 운영을 이유로 취소·재예약·즉시 완료하지 않는다. 준비비·참가자 수·종료 예정
시각·딜러 능력 결과를 바꾸지 않는다. 해제와 정산은 대회 처리만 담당한다.

신규 착석은 `canSeatNewGuests`가 판정한다. 대회 종료로 테이블이 `operating`으로
돌아와도 긴급 운영 중에는 유지 대상 하나만 손님을 받는다. 착석 가능 좌석과
이론 처리 능력도 같은 기준으로 줄어든다. 비용 계산은 정리·대회 자원의 비용을
정상 부과한다. 발동한 분에 이미 착석한 손님은 소급 취소하지 않는다.

**명령 제한.** 구매·고용·홍보·신규 대회 예약·수동 배치/교체/근무 전환을
`EMERGENCY_ACTIVE` 사유로 거절한다. 미래의 리모델링 동시 실행도 같은 관문에서
막힌다(리모델링 자체는 작업 C). 조회·예상치·저장과 기존 세션·대회의 자동 진행은
계속된다. 해금과 특별 직원 보상은 기존 조건대로 한 번 지급하되 자동 확장하지 않는다.

**복구 종료.** 9단계에서 축소를 적용한 뒤 아래를 모두 만족하면 종료한다.

- 유지 대상 테이블 1개와 딜러 1명이 실제 일반 영업 상태
- 다른 일반 테이블에 미완료 세션 없음, 다른 테이블 미운영, 다른 직원 대기
- 대회 없음, 잠긴 준비비 0
- 비용 지급 후 사용 가능 현금 >= 축소 완료 배치의 **분당 반복 비용 x 240분**

기준액은 새 상수가 아니라 기존 `minuteCosts`에서 파생한다. 현재 설정에서
일반 딜러 조합 600G, 숙련 딜러 조합 720G다. 종료하면 명령 제한이 풀리고,
**기존 배치를 자동 복원하지 않는다.** 유지하던 1개 테이블로 플레이어가 다시 확장한다.

**단계.** `DOWNSIZING`(축소 미완료) / `RECOVERING`(축소 완료, 자금 회복 대기).
고유 ID·시작 시각·유지 대상 ID·지원금 누계·지원 분 수를 상태에 보존한다.

### 7-3. 소규모 대회 예상치 (B-2C)

진입점: `forecastSmallTournament(state, tableIds, config, horizonMinutes = 1440)`

두 분기를 **같은 `tick()` 엔진으로 같은 게임 분만큼** 돌려 실제 기록값을 비교한다.
별도의 대회 시뮬레이터나 근사 공식을 만들지 않는다.

| 분기 | 내용 |
|---|---|
| baseline | 대회를 열지 않고 일반 영업을 계속한다 |
| tournament | 지금 예약하고 준비·진행·정산까지 실제로 치른다 |

**보고 항목을 계정별로 분리한다.** 일반 투자 예상치(`ForecastOk`)의 필드를
대회 회계로 재해석하지 않는다. 회수 시간(`paybackMinutes`)은 제공하지 않는다.

| 항목 | 출처 |
|---|---|
| 일반 세션 매출 | `records.totalRevenueUnits` 차이 |
| 대회 참가비 수입 | `records.totalTournamentRevenueUnits` 차이 |
| 반복 운영비 | 급여·시설비·매장비 누계 차이 |
| 대회 준비비 지출 | `records.totalOneOffUnits` 차이 (완료 시 1회) |
| 일반 완료 이용객 | `records.completedGuests` 차이 |
| 총현금 / 가용 현금 | `venue.cash`, `cash - lockedCash` |
| 완료 시각·인지도 이득 | `records.completedTournaments`의 완료 기록 |

준비비는 예약 시 **잠기기만** 하고 총현금에서 빠지지 않는다 (`cashAfterReservation`이
이를 드러낸다). 실제 지출은 완료 시점에 한 번 인식된다. 상금·참가자별 운영비·고정
개최비는 이미 준비비에 포함돼 다시 빼지 않고, 급여·시설비는 전역 틱이 부과하므로
대회 쪽에서 또 빼지 않는다.

`delta.ordinaryRevenueUnits`는 보통 **음수**다. 예약 테이블이 쉰 기회비용이며,
참가비만 떼어 "대회의 이득"이라 표현하지 말라는 `02 §8`의 요구가 이 구조로 드러난다.
결과를 내기 전에 `현금 차이 = 일반 매출 + 참가비 − 반복 비용 − 일회성 지출`이
맞는지 검사하고, 어긋나면 결과를 내지 않고 예외를 던진다.

**명시적 미지원으로 돌려보내는 경우**

| 코드 | 상황 |
|---|---|
| `COMMAND_REJECTED` | 예약 자격 미달. 기존 typed 사유를 그대로 전달 |
| `TOURNAMENT_ALREADY_ACTIVE` | 이미 대회가 걸려 있어 일반 영업 반사실을 복원할 수 없다 |
| `TOURNAMENT_INCOMPLETE_AT_HORIZON` | 지평 안에 끝나지 않았다. 지평을 늘리거나 정산을 지어내지 않는다 |
| `CASH_WENT_NEGATIVE` / `EMERGENCY_NOT_IMPLEMENTED` | 미구현 긴급 축소 운영이 필요한 구간 |

`02 §8`의 4게임시간 운영 예비금 규칙(R10)과 대회 생애주기는 이 작업에서 바꾸지 않았다.

### 7-2. 특별 직원 지급과 멱등성 (B-2B)

| 보상 | 조건 (Economy §5 / Progression §4) | 지급 |
|---|---|---|
| 숙련 딜러 1명 | 테이블 3개 설치 | 대기 상태, 미배치 |
| 대회 전문 딜러 1명 | 소규모 대회 1회 정상 완료 | 대기 상태, 미배치 |

기존 딜러를 교체하거나 자동 배치하지 않는다. 배치는 플레이어가 기존 `assignDealer`로 한다.
대기 직원은 급여가 없으므로(`Economy §5`) 지급만으로 비용이 늘지 않고 고용비도 없다.

**해금 기록과 지급 기록을 분리한다.**

| ID | 의미 |
|---|---|
| `skilledDealerGrant` | 자격 도달 기록. B-1부터 있었고 **직원을 만들지 않았다** |
| `skilledDealerAwarded` | 직원을 실제로 지급했다는 증거 |
| `tournamentSpecialistAwarded` | 위와 같음 |

자격 기록을 지급의 증거로 쓰면, 그 기록만 있고 직원을 못 받은 기존 v3 저장본이
보상을 영영 받지 못한다. 그래서 별도 ID를 쓴다. 조건은 해금 기록이 아니라
**상태에서 직접** 본다 (설치 테이블 수, `completedTournaments`의 소규모 완료 여부).
따라서 그런 저장본도 다음 틱에 정확히 한 번 보상을 받는다.

마커를 기존 `unlocks` 배열에 담으므로 **새 영속 필드가 없고 `saveVersion`도 오르지 않는다.**
지급은 기존 9단계(해금·보상·배치 전환)에서 일어나며, 8단계 비용 차감과
3단계 대회 처리보다 뒤이므로 그 분에 이미 시작된 세션·대회에 영향을 주지 않는다.
새로 받은 전문 딜러가 진행 시간을 줄이려면 플레이어가 그 딜러를 테이블에 배치하고
그 테이블을 다음 대회로 예약해야 한다 (R3).

### 7-1. 대회 회계 계정 분리 (B-2A)

| 계정 | 의미 |
|---|---|
| `records.totalRevenueUnits` | **일반 세션 매출만.** `= completedGuests x 200G` 불변식을 유지한다 |
| `records.totalTournamentRevenueUnits` | 대회 참가비 수입 |
| `records.totalOneOffUnits` | 일회성 지출. 대회 준비비가 완료 시 여기로 들어간다 |
| `records.totalEmergencySupportUnits` | 긴급 운영 지원금 (B-3). 현금에는 반영되지만 영업 성과가 아니다 |
| `totalWage/Facility/VenueCost` | 전역 반복 비용. 대회 중에도 그대로 부과되며 정산에서 다시 빼지 않는다 |

`venue.cash`는 위 계정을 모두 반영하는 **단일 잔액**이다. 두 번째 독립 잔액을 만들지 않았다.
참가비를 `totalRevenueUnits`에 더하지 않은 이유는 기존 검산·회귀 테스트가 그 값을
`완료 이용객 x 200G`로 대조하고 있기 때문이다 (`04 §1`, `tests/reconcile.test.ts`).

## 8. 검산 대조 원칙

`04`의 결과는 **비교 자료**로만 쓴다. 숫자를 맞추기 위한 보정값을 넣지 않는다.
차이가 나면 원인을 "의도한 정밀도 변경" / "구현 오류" / "문서 해석 차이"로 분류해 보고한다.

특히 **최소 잔액 265G는 근사치가 아니라 처리 순서의 결과**로 검증한다.

```
분당 비용 = 급여 80 + 테이블비 30 + 매장비 40 = 150G/시간 = 150 units/분
첫 손님 도착 = 분 15  (1.2×10^14 / 8.05×10^12 = 14.907 → 올림)
첫 세션 완료 = 분 135 (15 + 120)

분 134 종료 시점: 36000 - 150 × 134 = 15900 units = 265.00G   ← 최소 잔액
분 135: 4단계에서 +12000 units 정산 후 8단계에서 -150 → 27750 units = 462.50G
```

즉 265G는 "약 262.5G와 비슷한 값"이 아니라 **정확히 265G**이며, 최소값이 나타나는
**분 134라는 시점까지** 테스트가 검증한다.
